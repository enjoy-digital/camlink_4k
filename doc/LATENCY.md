# Latency

Status of the latency work (2026-09-30): what is measured, how, what is expected and what is next.
`doc/BENCHMARK.md` is generated by `software/bench.py report`; this file is kept by hand.

## Measured

| Date       | Firmware     | Source                   | Capture             | Render -> first byte | Render -> frame complete |
|------------|--------------|--------------------------|---------------------|----------------------|--------------------------|
| 2026-09-28 | CamLinX      | this PC HDMI-0, 4K30 RGB | YUYV 1920x1080@30   | ~3 ms                | ~35 ms                   |
| -          | Stock        | -                        | -                   | not measured         | not measured             |

- Method (`software/bench.py`, `software/source.py`): the host draws a barcode with its
  CLOCK_MONOTONIC time (ms) and a frame counter on HDMI-0, the capture decodes it; first byte =
  V4L2 buffer timestamp, frame complete = dequeue time. Source and capture share the host clock, so
  the Cam Link HDMI input must be this PC's HDMI-0 (and the screen unlocked, a locked screen blanks
  HDMI-0: the latency columns of `doc/BENCHMARK.md` are empty for that reason).
- Stock vs CamLinX, measured (`doc/BENCHMARK.md`): same fps and 0 drops, lower frame interval
  jitter, faster first frame (0.031 s vs 0.069 s at 1080p60, 0.098 s vs 0.264 s at 2160p30),
  lower capture CPU. Stock latency itself not measured yet (needs the stock firmware loaded in RAM
  from the flash backup directory, the user's call).

## Expected

- YUY2 / M420: line buffers only (no frame buffer), frame complete ~ one source frame period plus
  ~2 ms of USB transfer: close to the minimum for UVC (uvcvideo hands complete frames to the
  application).
- NV12 (4K30): through the DDR3 frame buffer (3 slots): up to one extra frame (~33 ms).
- Host: players add their own buffering (see below), often more than the device.

## Next

1. Measure: Cam Link on HDMI-0, `bench.py run` for all modes (CamLinX, and stock if loaded),
   including 2160p30 NV12.
2. Low latency NV12: start reading the Y plane while the writer is a few lines ahead (reader
   chasing the writer in the same slot, UV plane read once the frame is written): saves ~1 frame.
3. Device timestamps (PTS/SCR from the FPGA clock) for A/V sync and latency analysis without a
   shared clock.

## Manual check (mouse)

Low latency preview with ffplay (no demuxer/decoder buffering, late frames dropped, no audio
clock):

```sh
# 1080p60 (set the source to 1080p60), lowest latency mode:
ffplay -fflags nobuffer -flags low_delay -framedrop -sync ext -probesize 32 -analyzeduration 0 \
       -f v4l2 -input_format yuyv422 -video_size 1920x1080 -framerate 60 -i /dev/video0
# 4K30 NV12 (frame buffer path), scaled to fit the screen:
ffplay -fflags nobuffer -flags low_delay -framedrop -sync ext -probesize 32 -analyzeduration 0 \
       -f v4l2 -input_format nv12 -video_size 3840x2160 -framerate 30 -i /dev/video0 -vf scale=1920:-2
```

Move the source's mouse and watch the preview; for a number, film both screens with a phone at
high frame rate (240 fps) next to each other and count the frames between the two cursors.
