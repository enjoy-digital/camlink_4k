# Latency

Status of the latency work (2026-09-30): what is measured, how, what is expected and what is next.
`doc/BENCHMARK.md` is generated by `software/bench.py report`; this file is kept by hand.

## Per stage latency: stock vs CamLinX, ffplay vs viewer (2026-10-01)

1080p60, medians in ms from the source render (barcode with the host CLOCK_MONOTONIC ms on
HDMI-0), 20 s per run, barcode at the top or the bottom of the frame. Results:
`doc/bench/latency_display.json`, per sample viewer stages: `doc/bench/latency/*.csv`.

| Stage (time since the source render)                   | CamLinX top | CamLinX bottom | Stock top | Stock bottom |
|--------------------------------------------------------|-------------|----------------|-----------|--------------|
| Source frame buffer (HDMI-0 probe, calibration)        | 1.2         | 1.2            | 1.1       | 1.1          |
| First payload of the frame on USB (viewer)             | 3.7         | 3.5            | 35.1      | 34.0         |
| First payload, uvcvideo buffer timestamp (V4L2)        | 3.6         | 2.9            | 35.2      | 34.4         |
| Barcode rows on USB (viewer)                           | 7.3         | 18.2           | 37.5      | 44.0         |
| Frame complete, V4L2 dequeue (what ffplay gets)        | 19.4        | 18.9           | 46.1      | 45.3         |
| Viewer present call returned                           | 12.2        | 22.3           | 41.3      | 49.9         |
| **On screen (displayed frame buffer), camlinx_view**   | **34.6**    | **38.0**       | 69.5      | 68.4         |
| **On screen (displayed frame buffer), ffplay**         | 71.6        | 71.6           | 88.4      | 87.0         |

Where the time goes:

- **Device**: CamLinX sends the first payload of a frame ~3.5 ms after the render (source
  compositor + HDMI frame start + ~1 ms of line buffers/FX3 buffer), and streams the frame as it is
  scanned: the barcode rows arrive 3.5 ms (top, row 240) and 14.7 ms (bottom, row 1020) after the
  first payload, the HDMI scan times of those rows (1125 lines in 16.7 ms). **Stock buffers the
  frame**: its first payload leaves ~31 ms (~2 frames) later, then the frame is sent as a burst
  (rows 1020 in 10 ms, faster than the scan), so frame complete is 26-27 ms later than CamLinX.
- **uvcvideo**: delivers the frame at its end (dequeue ~19 ms CamLinX, ~46 ms stock), whatever
  the position of the pixel.
- **ffplay**: ~50 ms (CamLinX) / ~42 ms (stock) between the dequeue and the displayed frame
  buffer, even with the low latency options: the biggest stage of the default path.
- **camlinx_view**: present ~4-5 ms after the rows arrive (texture upload, render, present call),
  then **~22 ms (median) from the present to the displayed frame buffer**: the NVIDIA/X11 display
  path (flip/compositor), bimodal by one DP-1 refresh (top: p5 18.4 ms, median 34.6 ms; the
  previous campaign gave 22.7/50.5 ms top/bottom): the next stage to attack (direct scanout).
- The viewer also works with the stock firmware (UVC bulk, descriptors parsed): 69 ms instead of
  88 ms with ffplay, the stock frame buffering stays.

Totals (displayed frame buffer, top/bottom): CamLinX + viewer 34.6/38.0 ms, CamLinX + ffplay
71.6/71.6 ms, stock + viewer 69.5/68.4 ms, stock + ffplay 88.4/87.0 ms. Not included: the
monitor's scanout and processing (the same for all).

- Setup: this PC's HDMI-0 at 1920x1080@60 -> Cam Link input, YUY2 1920x1080@60 capture, players
  fullscreen on DP-1 (1920x1080@60), NVIDIA RTX 3080 (595 open driver), GNOME on X11, ffplay 4.4.2
  (`-fflags nobuffer -flags low_delay -framedrop -sync ext -probesize 32 -analyzeduration 0 -fs`).
- Method (`software/latency_campaign.sh` -> `software/latency_display.py`): `software/source.py`
  draws the barcode (redrawn every 4 ms: each frame carries the latest render before its scanout,
  the same bias for every configuration); `software/viewer/latgrab` polls the barcode region of
  DP-1 (XShm, ~1.3-1.8 kHz) and timestamps the first appearance of each value; `camlinx_view
  --latency` decodes the barcode from the incoming YUY2 data and timestamps the first payload of
  the frame, the transfer completing the barcode rows and the present; the V4L2 path is read with
  `software/v4l2cap.py` (buffer timestamp, dequeue time).
- Stock switching needs the CamLinX FPGA watchdog disabled first (it resets the FX3 without our
  heartbeat): done by `latency_campaign.sh`, which also restores CamLinX to the flash at the end.
- First campaign (2026-09-30, displayed frame buffer only): stock + ffplay 87.8/87.8 ms, CamLinX +
  ffplay 84.1/71.5 ms, CamLinX + viewer 22.7/50.5 ms (top/bottom): same picture, with the run to
  run spread of the display stage (one DP-1 refresh).

## Display stage experiments (2026-10-01)

CamLinX + `camlinx_view`, 1080p60, displayed frame buffer (median, p5-p95 in parentheses), same
method as above (labels `viewer_*` in `doc/bench/latency_display.json`):

| Variant                                              | Draw done after the rows arrive | Displayed, top     | Displayed, bottom  |
|------------------------------------------------------|---------------------------------|--------------------|--------------------|
| A: SDL renderer (present/swap)                       | ~5 ms                           | 21.8 (18.0-51.8)   | 37.7 (34.7-55.7)   |
| B: SDL + `__GL_MaxFramesAllowed=1 __GL_SYNC_TO_VBLANK=0` | ~6 ms                       | 37.4 (34.5-54.4)   | 37.7 (34.2-56.2)   |
| C: `--front` (OpenGL front buffer rendering)          | **0.1-0.3 ms**                  | **20.0 (17.9-36.6)** | **36.4 (34.2-53.0)** |

- Front buffer rendering removes the viewer's present cost (~5 ms -> ~0.2 ms) and the long tail
  (top p95 52 -> 37 ms): the best variant. The NVIDIA frame queue limit does not help.
- The NVIDIA OSD (`__GL_SHOW_GRAPHICS_OSD=1`) shows **BLIT, not FLIP**, even fullscreen and
  unobstructed: the X screen spans both monitors (3840x1080) and NVIDIA only flips windows covering
  the whole X screen, so GNOME's compositor (mutter) composites the window on DP-1's frame clock.
  The remaining 13-18 ms after the draw is that composition, quantized to DP-1 refreshes (the
  run to run "one refresh" spread).
- Next: no compositor on the display (direct scanout of a monitor leased from the desktop, or a
  single monitor session), a high refresh monitor (the floor drops from 16.7 ms to 4-7 ms).
- The viewer activates its window with a pager `_NET_ACTIVE_WINDOW` request (a plain raise is
  ignored by GNOME's focus stealing prevention when another window has the focus; an obstructed
  window is always copied).

## Expected

- YUY2 / M420: line buffers only (no frame buffer), frame complete ~ one source frame period plus
  ~2 ms of USB transfer: close to the minimum for UVC (uvcvideo hands complete frames to the
  application).
- NV12 (4K30): through the DDR3 frame buffer (3 slots): up to one extra frame (~33 ms).
- Host: players add their own buffering (see below), often more than the device.

## Low latency viewer

`software/viewer/camlinx_view` (C, libusb + SDL2) removes the whole frame wait of uvcvideo: it
detaches uvcvideo from the streaming interface, starts the stream with a UVC PROBE/COMMIT, reads
the bulk payloads (16 x 128KB transfers in flight) and uploads/presents the new rows as they
arrive (vsync off by default: the display races the incoming frame, like a tearing monitor). A
pixel is on screen ~0.5 ms after its USB transfer completes instead of at the end of the frame
(saves up to one frame: 16.7 ms at 60 fps, 33 ms at 30 fps). uvcvideo gets the interface back on
exit (V4L2 applications work again).

```sh
make -C software/viewer
software/viewer/camlinx_view                                    # YUY2 1920x1080@60 (default)
software/viewer/camlinx_view --size 1920x1080 --fps 30          # 4K30 source, 2x downscale
software/viewer/camlinx_view --format m420 --size 3840x2160 --fps 30 --fullscreen  # 4K30 direct
software/viewer/camlinx_view --front --fullscreen                # Lowest latency (YUY2, front buffer)
```

`--front` (YUY2): OpenGL front buffer rendering (shader YUY2 -> RGB, only the new rows drawn, no
swap), the lowest latency mode (see the display stage experiments). Also with the stock firmware
(`--device stock`, YUY2 at the input mode): the streaming interface,
endpoint and format/frame indexes are read from the UVC descriptors. `--latency [--csv file]`:
per stage timestamps from the source barcode (see above).

Keys: `f` fullscreen, `q`/Esc quit. `--vsync` presents on vsync (no tearing, up to one display
refresh more). Checked with a MacBook 4K30 source: YUY2 1080p30 30 fps / 124.5 MB/s (~11 row
slices per frame), M420 4K30 30 fps / 373.4 MB/s (~100 slices per frame), 0 header errors, 0 bad
frames, uvcvideo capture OK afterwards.

## Manual check (mouse)

Low latency preview with ffplay (no demuxer/decoder buffering, late frames dropped, no audio
clock):

```sh
# 1080p60 (set the source to 1080p60), lowest latency mode:
ffplay -fflags nobuffer -flags low_delay -framedrop -sync ext -probesize 32 -analyzeduration 0 \
       -f v4l2 -input_format yuyv422 -video_size 1920x1080 -framerate 60 -i /dev/video0
# 4K30 NV12 (frame buffer path), scaled to fit the screen:
ffplay -fflags nobuffer -flags low_delay -framedrop -sync ext -probesize 32 -analyzeduration 0 \
       -f v4l2 -input_format nv12 -video_size 3840x2160 -framerate 30 -i /dev/video0 -vf scale=1920:-2
```

Move the source's mouse and watch the preview; for a number, film both screens with a phone at
high frame rate (240 fps) next to each other and count the frames between the two cursors.
