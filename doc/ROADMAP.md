# LiteCamLink Roadmap

Where LiteCamLink stands, how it will be compared against the stock Elgato firmware, what to improve
first and which new features could make it attractive to users. Phase history and hardware notes are
in [PLAN.md](PLAN.md) and [HARDWARE.md](HARDWARE.md).

## Current State (2026-09)

| Area                  | Status                                                                                  |
|-----------------------|-----------------------------------------------------------------------------------------|
| Boot / dev loop       | FX3 firmware RAM-loaded by the host (`camlink.py boot`), FPGA loaded through the FX3.   |
| USB                   | SuperSpeed, UVC 1.1 bulk, works with uvcvideo / ffmpeg / VLC without kernel quirks.     |
| Formats / modes       | YUY2 640x480, 1280x720, 1920x1080 at 30/60 fps.                                         |
| HDMI input            | IT6802 init + own EDID + HPD, SDR (<= 1080p) and DDR (4K) capture, 4K30 -> 1080p30.     |
| Throughput            | ~300 MB/s sustained (GPIF 96 MHz x 32-bit), 1080p60 YUY2 at 59.94 fps.                  |
| Colour                | AVI InfoFrame driven CSC (RGB -> YUV or bypass), BT.709, verified on colour bars.       |
| DDR3                  | 128 MB DDR3L working (BIOS memtest), not used by the video path yet.                   |
| Audio                 | Not implemented.                                                                        |
| Known issues          | First frame after stream start lost, ZLP after short payloads, host-loaded only.        |

## 1. Benchmarking Against the Stock Firmware

The stock FX3 image can be RAM-loaded from the flash backup (`<backup dir>/stock_fx3.img`), and
it loads the stock bitstream still present in flash: the same unit, cable and source can be tested
with both firmwares, switching in a few seconds and without writing the flash.

A `software/bench.py` harness will run each test on both firmwares and write the results to
`doc/BENCHMARK.md` (tables + captured images).

### Metrics

| Metric                | Method                                                                                     |
|-----------------------|--------------------------------------------------------------------------------------------|
| Latency               | Source shows a frame counter / timestamp; the capture host decodes it and compares with its own clock. Requires the source and the capture on the same machine (Cam Link on this PC's HDMI output). Also: device-side latency from PTS/SCR. |
| Frame pacing          | fps, jitter, dropped and duplicated frames from V4L2 buffer timestamps and frame counters, over long runs. |
| Image quality         | Same test content (colour bars, zone plate, fine text, gradients) captured by both: PSNR/SSIM vs reference, chroma accuracy, black/white levels, banding. |
| Modes and formats     | Resolutions, frame rates and pixel formats actually delivered for each input mode.          |
| Robustness            | Time to first frame, signal loss / cable replug, resolution change while streaming, 100+ start/stop cycles, host suspend. |
| Compatibility         | Linux without `UVC_QUIRK_FIX_FORMAT_INDEX`, Windows and macOS class drivers, OBS, browsers (WebRTC). |
| Host cost             | CPU load and USB bandwidth per format (YUY2 / NV12 / future compressed formats).            |

### Bench setup

- Automated: Cam Link HDMI input on a host output (this PC's `HDMI-0`), content and timestamps
  generated by the capture host itself (`xrandr` modes + full screen test player).
- Manual/complementary: external sources (MacBook Pro 4K30, game consoles, cameras).
- Optional: YKUSH for power cycling, logic analyzer for I2C/timing investigations.

## 2. Improvements (Gaps vs Stock)

| # | Item                          | Description                                                                              |
|---|-------------------------------|------------------------------------------------------------------------------------------|
| 1 | Standalone boot               | Flash our FX3 image + bitstream so the device works without the host loader; keep a safe recovery path (USB boot fallback, stock image restore tool). **Done**: flash boot + `flash-recover` validated on hardware. |
| 2 | 4K30 full resolution          | NV12 output + USB throughput to ~380 MB/s (bigger/more DMA buffers, GPIF at ~100 MHz); 4K30 NV12 needs ~373 MB/s. |
| 3 | Native 1080p60 input          | Validate the IT6802 SDR path (1 pixel/clock) and its clock phase window.                 |
| 4 | Audio (UAC)                   | I2S capture in the FPGA, in-band transfer through the GPIF, UAC 1.0 stereo 48 kHz, A/V sync. |
| 5 | Stream/signal robustness      | Fix the first-frame loss, clean handling of signal loss and input mode changes while streaming, "no signal" screen. |
| 6 | Better downscaling            | Proper 2x2 box filter (line buffer) instead of line dropping; later a generic scaler.     |
| 7 | Input-matched modes           | Report/offer the input mode the way stock does (dynamic descriptors) or scale to the requested mode. |

## 3. New Features (Not in Stock)

| Feature                         | Why it matters                                                                          |
|---------------------------------|-----------------------------------------------------------------------------------------|
| Low-latency mode                | Line/slice based streaming without frame buffering, for gaming and live monitoring; built-in latency measurement. |
| Fixed output mode               | Always deliver 1080p60 (or a chosen mode) whatever the input, with scaling/letterboxing: OBS scenes and video calls never break on source mode changes. |
| 4K crop / zoom                  | Pixel-exact 1080p window anywhere in a 4K desktop (screen recording, tutorials, demos).  |
| Host-programmable EDID          | Choose advertised modes (1440p, 1080p120 within 300 MHz TMDS), or clone the monitor's EDID for pass-through setups. |
| Input information for apps      | Resolution, frame rate, colour space/range, audio format, hotplug events exposed through a UVC extension unit and the CLI. |
| Accurate timestamps             | Device PTS/SCR from the FPGA clock for A/V sync and latency analysis.                    |
| Colour controls                 | Range (full/limited) and colour space override, levels, optional LUT.                    |
| DDR3 based features             | Freeze frame, frame-rate conversion, instant replay buffer.                              |
| 10-bit capture                  | To be evaluated: IT6802 20/24-bit 4:2:2 modes vs the 24 wired data lines.                |
| Self-test / test patterns       | Built-in patterns (bars, moving, frame counter) for setup and debugging, loopback tests.  |
| Open, scriptable device         | CLI/API for automation, reproducible builds, no vendor tools required.                   |

## 4. Suggested Order

1. **Benchmark harness** (stock vs LiteCamLink): baseline numbers before any optimization.
2. **Latency**: measurement, then low-latency mode.
3. **Standalone boot** + recovery/update tool.
4. **4K30 NV12** (USB throughput work) and native 1080p60 validation.
5. **Audio**.
6. Feature work driven by the benchmark results and user feedback (fixed output mode, crop/zoom,
   custom EDID, extension unit).

## Open Questions

- Stock 4K30 NV12 throughput: how close to the FX3 limit does the stock firmware run?
- IT6802 10-bit output mapping onto the 24 wired lines.
- Best host API for extension-unit controls (v4l2 controls via uvcvideo XU mapping vs vendor requests).
